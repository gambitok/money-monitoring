# CLAUDE.md

Контекст для Claude Code у цьому репозиторії.

**money-monitoring** — локальний облік доходів і витрат для одного користувача. Щоденне введення операцій, власні категорії, зведена таблиця і імпорт старих витрат з власної Excel-таблиці (`.xlsx`). Тільки гривня. Без авторизації, працює на localhost.

План і статус етапів: @docs/plan.md

## Як працювати

- Спілкуйся українською. Код, ідентифікатори, коміти англійською.
- Власник має 7+ років досвіду (PHP/Laravel, JS/TS, Vue). Базові речі не пояснюй.
- Роби один етап з плану за раз. Після етапу онови статус у `docs/plan.md`.
- Нових залежностей не додавай без потреби. Кожну нову залежність спочатку погодь.
- Коміть лише на прохання власника.

## Стек

- Node.js 24, ESM (`"type": "module"`).
- **Express 5.** Він сам ловить rejected async handlers, тому обгортка `route()` як у token-monitoring не потрібна.
- **better-sqlite3**: синхронний API, файл `data/money.db`, `journal_mode = WAL`, `foreign_keys = ON`.
- Фронтенд: vanilla JS + HTML + CSS у `public/`, без фреймворку і бандлера.
- Тести: вбудований `node:test`. Сервер піднімається на випадковому порту з БД у тимчасовому файлі, запити робляться через `fetch`.
- Порт за замовчуванням `3001` (порт 3000 зайнятий token-monitoring), можна змінити через `PORT`.

## Команди

- `npm install`, `npm start` → http://localhost:3001. `npm run dev` перезапускає сервер при зміні файлів (`node --watch`). Зміни в `public/` потребують лише оновлення сторінки.
- `npm test`: `node --test` знаходить `tests/*.test.js`. `tests/helpers.js` має `startTestServer()`, який створює тимчасову БД і повертає `{ db, baseUrl, close }`.
- `launch.ps1`: запускає сервер, якщо він не працює (перевіряє `/api/health`), і відкриває браузер.
- Перевірка UI в браузері — **тільки** через конфіг `money-monitoring-demo` у `.claude/launch.json` (порт 3002, `DB_FILE=data/demo.db`). Конфіг `money-monitoring` працює з реальною `data/money.db`, тож тестові операції через нього не вводь.
- Змінні оточення: `PORT` (3001), `DB_FILE` (`data/money.db`).

## Модель даних

Схема — у міграції 1 в `src/db.js`. Міграція 2 додає стартові категорії власника (`DEFAULT_CATEGORIES_V2`: 11 витрат, 5 доходів). Вона пропускає назви, які вже є (без урахування регістру), і виконується один раз, тож видалені користувачем категорії не повертаються. Цей список не редагуй: нові дефолти додавай окремою міграцією. Міграція 3 додає `budgets` (плани на місяць, діють щомісяця): `type`, `category_id` (NULL — загальний план типу), `amount_minor`. Partial unique indexes дозволяють один загальний план на тип і один план на категорію, а тригери перевіряють, що тип категорії збігається з типом плану. `ON DELETE CASCADE` по категорії. Коли категорія змінює тип, `categories` PATCH видаляє її план. Через сід свіжа БД (і в тестах теж) уже містить категорії, тому тести, яким потрібен порожній список, роблять `DELETE FROM categories` у `beforeEach`. Дві таблиці:

- `categories`: `name`, `type` (`income`/`expense`), `color`, `archived_at`, `created_at`. Пара `(name, type)` унікальна.
- `transactions`: `type`, `amount_minor`, `currency` (`'UAH'`), `occurred_on` (`YYYY-MM-DD`), `category_id` (nullable), `description`, `source` (`manual`/`import`), `import_hash` (унікальний, nullable), `created_at`, `updated_at`. Індекси по `occurred_on` і `category_id`.

Часові мітки — ISO UTC з мілісекундами (`strftime('%Y-%m-%dT%H:%M:%fZ','now')`). `updated_at` при UPDATE оновлює код, тригера на це немає.

**Інваріанти, які БД гарантує сама** (CHECK, FK і тригери; тести в `tests/schema.test.js`):
- `amount_minor` — ціле число більше 0. Числовий рядок SQLite приводить до INTEGER через affinity.
- `occurred_on` — реальна дата: `date(x) IS x`, тож `2026-02-30` не пройде.
- Без категорії потрібен непорожній опис.
- Тип категорії збігається з типом операції (тригери на INSERT і UPDATE).
- Категорію з операціями не можна видалити (FK RESTRICT) і не можна змінити їй тип (тригер). Її можна лише архівувати.

Валідація в API дублює ці правила, щоб повернути зрозумілі помилки. Для помилок констрейнтів, які до API не дійшли, БД — остання лінія захисту.

## Правила домену

- **Гроші зберігаються цілим числом у копійках** (`amount_minor`), float не використовуємо. Конвертація з введеного користувачем рядка і назад відбувається на межі системи (валідація API і форматування в UI).
- Знак суми не зберігаємо: напрям операції задає `type`, сума завжди більша за 0.
- Категорія необов'язкова. **Якщо категорії немає, опис обов'язковий.**
- Тип категорії має збігатися з типом операції.
- Категорію, до якої прив'язані операції, не видаляємо, а архівуємо (`archived_at`). Архівні категорії не показуються у формі, але залишаються у звітах.
- Дата операції — це календарний день без часу і часових поясів. За замовчуванням у формі стоїть сьогоднішня локальна дата.
- Агрегати (зведення, підсумки) рахуються в SQL (`GROUP BY`), а не в браузері.

## Схема коду

- `server.js`: тільки точка входу (відкриває БД, слухає порт, graceful shutdown).
- `src/app.js`: `createApp({ db })` збирає Express-застосунок (JSON-парсер, `/api/*`, JSON 404 для невідомих `/api`, статика, error handler). Тести імпортують саме його. Error handler віддає `err.status` з `err.message`, а для 5xx — загальне повідомлення.
- `src/db.js`: `openDb(file)` і `migrate(db, list)`. Масив `migrations` тільки доповнюється, номер версії = індекс + 1 і зберігається в `PRAGMA user_version`. Кожна міграція виконується у власній транзакції. Якщо БД новіша за код, `migrate` падає.

- `src/validate.js`: `parseAmount`, `isValidDate`, `validateTransaction`, `validateCategory`. Валідатори кидають `ValidationError` (status 400, `fields`: поле → повідомлення українською), а error handler віддає `400 { error, fields }`. `validateTransaction` приймає повний об'єкт: для PATCH спершу злий збережений рядок із патчем. Існування і тип категорії валідатор не перевіряє, це робить роут через БД.
- `parseAmount`: пробіли (зокрема NBSP і narrow NBSP) — роздільник тисяч. Один `,` або `.` — десятковий роздільник. Якщо є обидва, десятковий той, що останній, і ціла частина має бути правильно згрупована. `"1,234"` відхиляється, а не читається як 1234. Максимум 2 знаки після коми, сума до `MAX_AMOUNT_MINOR`. Числа з Excel пропускаються з допуском на похибку float.

- `src/routes/*.js`: окремий роутер-фабрика `xxxRouter(db)` для кожного ресурсу (`transactions`, `categories`, `summary`). `params.js` містить `parseIdParam` (некоректний id дає 404, а не 400) і `pick` (whitelist полів із тіла запиту). Помилка з `err.details` додає ці поля у JSON-відповідь, наприклад `conflict_id`.
  - `transactions`: відповідь рядка завжди включає `category_name` і `category_color` (LEFT JOIN). `GET /` повертає `{ items, totals: { income, expense, balance } }`, сортування `occurred_on DESC, id DESC`. Фільтри: `from`, `to` (включно), `type`, `category_id` (id або `none` для операцій без категорії). POST і PATCH беруть лише `EDITABLE_FIELDS`, тож `source`, `import_hash` і `currency` клієнт не задає. PATCH зливає збережений рядок із патчем і валідує результат. Нове `amount` перекриває збережене `amount_minor`. Архівну категорію не можна призначити заново, але вона лишається на операції, яка вже її мала.
  - `categories`: сортування через `Intl.Collator('uk')` у JS, бо SQLite сортує за кодами символів (Є, І, Ї опиняються перед А, а Ґ після Я). `include_archived=1` повертає й архівні. Кожен рядок містить `transaction_count`. Унікальність назви перевіряє `assertUniqueName` через `toLocaleLowerCase('uk')`, бо індекс `UNIQUE(name, type)` чутливий до регістру, а `NOCASE` розуміє лише ASCII. Конфлікт дає `409 { fields.name, conflict_id }`. Тип змінюється лише поки немає операцій (так само гарантує тригер). `DELETE` невикористану категорію видаляє, а використану архівує: `{ deleted, archived, category? }`.
- `public/`: нативні ES-модулі без бандлера.
  - `app.js`: точка входу, hash-роутинг (`#/` — головна, `#/ops` — операції, `#/month` — місяць, `#/summary` — зведення, `#/stats` — статистика, `#/categories` — категорії). Перемикає `hidden` у `#viewXxx` і викликає `showXxxView()`, коли в'юха стає видимою (оновити дані).
  - `lib.js`: `h(tag, attrs, ...children)` для DOM (текст через text nodes, `style` через `setProperty`, `value` як властивість), `api()` і `ApiError` (`status`, `body`, `fields`), дати (UTC за календарними днями, тиждень з понеділка), гроші (`formatMoney`, `formatSigned`, `minorToInput`), `plural()` з `Intl.PluralRules('uk')`, `readPref`/`writePref` (`localStorage` з try/catch).
  - `categories-store.js`: єдине джерело категорій на сторінці. `load`, `create`, `update`, `remove` перезавантажують список і сповіщають підписників (`subscribe`). `nextColor(type)` повертає перший колір `PALETTE`, якого ще немає серед активних категорій цього типу.
  - `home-view.js`: «Головна» (`#/`, стартова). Місяць (за замовчуванням поточний, ‹ ›) з `GET /api/dashboard`. Плитки: доходи й витрати з % від плану і смужкою, баланс, «можна витрачати / день» (залишок плану / днів лишилось, з сьогодні) або середнє на день без плану, порівняння з минулим місяцем, «≈ $X». Далі план і факт по категоріях витрат і доходів, останні операції з ✎. Кольори за правилом власника для витрат: < 85 % плану — `plan-ok` (зелений), 85–100 % — `plan-warn` (жовтий), понад план — `plan-over` (червоний). Для доходів досягнутий план зелений, інакше нейтральний прогрес. Риска `plan-pace` показує рівномірний темп на сьогодні. Кнопка «Плани» відкриває редактор, який зберігає весь набір через `PUT /api/budgets`. Посилання на день ведуть на `#/ops`.
  - `tx-modal.js`: спільна модалка (`<dialog>`) для додавання, редагування й видалення операції з будь-якої вкладки. `openTxModal({ tx })` редагує, `openTxModal({ defaults })` додає, `openTxModal({ list, title, defaults })` показує кілька операцій на вибір (клітинка з кількома операціями, «Разом» дня) з кнопкою «+ Додати ще». Після кожного збереження чи видалення викликає `onChanged()`, щоб вкладка перезавантажила дані. Валідацію показує під полями з `err.fields`.
  - `transactions-view.js`: форма вгорі **лише додає**; ✎ у списку відкриває модалку. Список за день або тиждень. `state.selectedCategoryId` — джерело правди для вибраної категорії, а `<select>` лише відображає його. Спеціальна опція `__new` відкриває рядок створення категорії, де Enter створює категорію, а не відправляє форму. Після збереження форма лишає тип, дату і категорію. Якщо дата поза поточним періодом, список переходить на неї. `loadSeq` відкидає застарілі відповіді. Режим day/week зберігається в `mm.mode`.
  - `month-view.js`: вкладка «Місяць» (`#/month`) у вигляді старої таблиці власника: рядок на кожен день місяця, колонки — категорії витрат (активні в порядку `id`, бо сід іде в порядку колонок старої таблиці; архівні — лише якщо використані; «Інше» останньою; «Без категорії», якщо є), «Разом» за день, описи дня, рядок підсумків, а праворуч доходи місяця. Будується на клієнті з `/api/transactions?from&to`, окремого API немає. Кілька операцій однієї категорії за день складаються, деталі — в `title`. Клітинки — кнопки: одна операція відкриває редагування, кілька — список; порожня клітинка додає витрату з цією датою й категорією. «Разом» дня тільки для читання (так захотів власник), перед ним вертикальний роздільник `.month-sep` на всю висоту таблиці. Після змін таблиця перезавантажується, опис дня й далі збирається з описів усіх операцій дня. Підсвітка за правилом власника: понад 2 000 ₴ — `heat-1`, понад 10 000 ₴ — `heat-2` (`HIGHLIGHT_STEPS`), а не відносно максимуму. Фон рядка задає `--row-bg` (вихідні — `surface-2`). Доходи — окрема картка під таблицею з «+ Додати дохід» і ✎. Під плитками доходів, витрат і балансу виводиться «≈ $X» за курсом з `/api/usd-rate` за місяць. Якщо запит падає (старий сервер), таблиця все одно будується.
  - ✎ у списках «Зведення» (деталізація) і «Статистики» теж відкриває модалку й після змін перезавантажує свою вкладку.
  - `stats-view.js`: вкладка «Статистика» (`#/stats`) показує, що купувалося, на скільки і як часто. Фільтри: тип, період (список «Весь час» або рік, чи свої дати), чипи категорій (мультивибір; порожньо — усі), пошук в описі з debounce. Блоки: плитки, «По категоріях» (клік лишає одну категорію), «По місяцях», «Найчастіші описи» і «Слова» (клік додає в пошук), список операцій.
  - `summary-view.js`: період — кнопки `3m`, `6m`, `12m` або цілий рік `y:YYYY` у випадаючому списку `#summaryYear`. Опції списку беруться з `GET /api/summary/years` (роки, в яких є операції, плюс поточний). Сторінка завжди відкривається на поточному році, вибір не запам'ятовується (так захотів власник). Поточний рік закінчується поточним місяцем, щоб не розмивати середні. Можна задати й довільні `<input type=month>`. Відносний пресет перераховується при кожному показі сторінки. Таблицю будує `render()` (суми округлено до гривні, точна сума в `title`). Теплова підсвітка — це `--heat` від 0 до 1 відносно найбільшої клітинки секції. Drill-down (`state.drill`: `type`, `categoryId` = id, `'none'` або `undefined`, `month` або `undefined` для всього періоду) тягне `/api/transactions`. `goToDay()` з `transactions-view.js` відкриває день в «Операціях».
  - `categories-view.js`: повністю перемальовує список на кожну зміну в store (`render()`). Inline-стан у `state.editingId` і `state.rowError`.
- CSS: `.view` — це grid з `grid-template-columns: minmax(0, 1fr)`. Без `minmax(0, …)` широка таблиця розтягує колонку ширше за сторінку. Класи `.income` і `.expense` фарбують текст, тож на контейнери їх не вішай (для секцій зведення є `section-income` і `section-expense`).
- `element.replaceChildren(a && b)` виводить текст `"false"`, тому falsy-частини фільтруй або передавай їх через `h()`, який їх пропускає.

  - `summary`: агрегація `GROUP BY type, category_id, substr(occurred_on, 1, 7)` в одному запиті, далі pivot у JS. Діапазон `[from-01, nextMonth(to)-01)`. Поле `usd: { rate, source } | null` (спільна логіка в `src/usd.js`, `createUsdRate(db)`; її ж використовують `stats` і `GET /api/usd-rate?from&to` з `routes/usd.js`, який потрібен вкладці «Місяць») — середній зважений курс долара (сума ₴ / сума $) за доходами з описом «$X за курсом Y» (фриланс з імпорту) за період. Якщо таких доходів у періоді немає, береться середній за весь час (`source: 'all'`). На клієнті під плитками виводиться «≈ $X» і рядок з курсом. Порожні місяці заповнені нулями, щоб клієнт не перевіряв `undefined`.

  - `budgets`: `GET /api/budgets`, `PUT /api/budgets { items: [{ type, category_id|null, amount }] }` замінює весь набір в одній транзакції; порожня сума означає «без плану». Валідація по кожному елементу (`items.N` у `fields`).
  - `dashboard`: `GET /api/dashboard?month=YYYY-MM&today=YYYY-MM-DD` (локальна дата клієнта задає `day_of_month`: 0 для майбутнього місяця, `days` для минулого). Повертає `income`/`expense` `{ actual, plan }`, `balance`, `categories` (кожна категорія з планом або грошима за місяць; архівні лише з грошима; «Без категорії» з `category_id: null`), `previous` (суми минулого місяця), `recent` (8 останніх), `usd`.
  - `stats`: `GET /api/stats?from&to&type&category_ids&q`. Діапазон і категорії фільтрує SQL, пошук робить JS (`parseQuery`/`matchesQuery`: кома — «або», пробіл — «і», без урахування регістру, зокрема кирилиці), бо SQLite `LIKE` розуміє лише ASCII. Повертає `totals`, `byCategory`, `byMonth`, `topDescriptions` і `words`, де count — **кількість різних днів** (імпорт ділить один день на кілька сум зі спільним описом). Також повертає `items` (до 1000), `truncated` і `usd` (курс за період, як у `summary`). На клієнті під плитками «Сума», «Середня операція» і «В середньому / міс» виводиться «≈ $X». Через спільні описи дня пошук по старих даних зачіпає й інші категорії того дня, тож для точності його поєднують з фільтром категорії.

## Імпорт старих витрат

Робить Claude на прохання власника, а не UI. Власник вставляє в чат текст зі своєї старої таблиці (TSV з Excel).

1. Збережи текст як є (з табами й порожніми клітинками) у `data/import/<рік>-raw.tsv`. Ця папка gitignored, у ній особисті дані. Перевір структуру: `awk -F'	' '{print NF}'`.
2. Пробний прогін: `node scripts/import-legacy.js data/import/<рік>-raw.tsv --year <рік> --recategorize`. Скрипт звіряє розпізнані суми з рядками «разом» у таблиці й показує виправлені місяці, попередження і перенесені за описом операції.
3. Імпортуй у `data/demo.db` (`--commit --db data/demo.db`) і подивись зведення через конфіг `money-monitoring-demo`.
4. Покажи власнику звіт і спірні місця. **Лише після його «так»** запусти з `--commit` по `data/money.db`. Скрипт сам робить бекап `money.db.bak-<час>` (після `wal_checkpoint`) і пише все в одній транзакції.

`src/import/legacy-sheet.js` (`parseLegacySheet`): формат — місячні блоки, заголовок із колонок-категорій (порядок буває різний, тож кожен заголовок перемапить колонки), рядки `DD.MM`, опис після колонок і подеколи ще колонка з напоями. Особливості реальних даних описані в шапці файлу й у `tests/legacy-sheet.test.js`. Дати, що йдуть назад, переносяться в наступний місяць. Рядки після підсумків блоку (план або бюджет) ігноруються. Мапінг колонок — `LEGACY_COLUMNS` (Таксі → Транспорт, Дім → Товари для дому, Комуналка → Комунальні платежі). `--recategorize` переносить з «Інше» чи «Комуналка» за `RECATEGORIZE_RULES`, лише коли опис стосується єдиної суми в рядку. Правило з `words` вимагає, щоб увесь опис був одним словом зі списку. Правило з `contains` спрацьовує, якщо слово є будь-де в описі (Криптовалюта: binance, біток). Категорію з правила, якої ще немає в БД, скрипт створює сам. Доходи (формат 2025): колонки `INCOME_COLUMNS` праворуч від витрат. Беремо рядок підсумку доходів блоку (число одразу за останньою колонкою доходів): «хое» і «токо it» читаються зі своїх колонок, а фриланс = разом − зарплати. Курс 30..60 з комою береться з тієї ж зони. Дата — 1-ше число місяця, хеш `legacy-income:<YYYY-MM>:<джерело>`. Формат 2026: явні колонки Заклади, Транспорт, Підписки, Здоров'я, а також «Дата» і «Коментар» у заголовку. Курс записаний цілим числом у колонці «долар»/«usd». Якщо в рядку сум немає клітинки «разом», рядком сум вважається той, де «хое» дорівнює сумі виплат вище. Перший блок, підписаний пізнішим місяцем, ніж наступний («12» перед «02»), переноситься на місяць перед наступним. Правило `contains` для «Інше» спрацьовує, навіть коли в рядку кілька сум з описом. `import_hash` = `legacy:<дата>:<колонка>`, тож повторний запуск нічого не дублює. Інший формат таблиці — новий парсер поруч, не латки в цьому.

## Застереження

- `data/` у `.gitignore`, там лежать реальні дані власника. Ніколи не видаляй і не перезаписуй `data/money.db`. Тести працюють лише з тимчасовою БД.
- У фронтенді будь-який текст користувача (опис, назва категорії) вставляй через `textContent` або екрануй. Інтерполяція сирих значень у `innerHTML` заборонена.
- Багатокрокові записи (імпорт, масові дії) виконуй у `db.transaction(...)`.
